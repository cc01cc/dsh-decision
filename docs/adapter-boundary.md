# DSD 薄适配器边界声明

> **状态**：现行边界声明（未实施代码）· **日期**：2026-11-13 · **卡片**：`task-329`
> **用户裁定原话**：「**做薄适配器，不做权限体系。**」
> **依据**：`task-313` / `task-314` / `task-320` / `task-322` 的实测 + `D-1157` / `D-1164` / `D-1168`。
> **本文的定位**：回答「CLI 这一层**是什么、做多少、不做什么、和 DSH 插件怎么分工**」。不回答「要不要做 CLI」（那是用户的裁定）。

---

## 0. 一句话结论

**CLI 是 DSD 在现有注入缝上的第二个适配器，不是一个新的权限边界。**

三句话展开：

1. **缝已经在代码里**（`DecisionToolDeps` 四字段全注入、`registerDecisionTools` 收结构 sink、92 项测试零 DSH 依赖）⇒ 加 CLI 是**认出已有的缝**，不是设计一条缝。
2. **它只买到两样东西**：调用面（脚本 / CI / 其他工具能调）与更短的调试回路（`D-1157` 用户原话）。它**买不到**访问控制——同用户任意进程可 `node -e` 直写 sqlite，代价一行（`task-313` §2.2 [实测]）。
3. **归因退化到 OS 账户级别**：CLI 写入的「谁做的」只能记成**自报**，事后能追但不可信。这是本文的诚实底线，不许在任何文档里把它包装成「安全的」。

## 1. 先纠正两条前提（不纠正就会把 CLI 的理由建在沙子上）

### 1.1 「DSH 不能重启，所以只能走 CLI」—— 已不成立

这条前提在 2026-11-13 之前被反复使用（含本文件作者）。实测推翻（`task-314` / `task-320` / `task-322`）：

| 源码落点 | 只改源码文件 | 改完再触发一次重组合 | 需要重启？ |
| --- | --- | --- | --- |
| A：profile 目录内 + `hmr.config.root: ["."]` | **自动热更**（同 pid） | 不需要 | **不需要** [实测] |
| B：profile 目录内，`root: []`（desktop 默认） | 不生效 | **热更生效**（碰一下 patch） | **不需要** [实测] |
| C：profile 之外的绝对路径 | 不生效 | **仍不生效** | 需要（或改落点）[实测] |
| D：链接包（`node_modules` junction）+ 包名引用 | 不自动 | **热更生效** | **不需要** [实测] |

补充读数（同包 §4.2 / §9）：

- **把条目加进 patch 本身就是热的**：三次切换落点（本地路径 → junction 包名 → 改包源码）都是同一个 pid 直接 `apply`，**新插件首次挂载也不需要重启** [实测]。
- **desktop profile 的 HMR 监听在活进程里确实在跑**：写入后 **2.14 s** 出现 `dsh-hmr-clock-*`（重组合标志），还原后 **2.06 s** 再次出现；全程 `pid 70616` / `16720` 存活、64568 端口全程在听；结束时 **byte-identical（5752 B / 195 行 / mtime 复原）** [实测]。

⇒ **「必须新起 DSH」这句话不许再出现在任何文档、卡面、报告里。** 唯一仍需重启的情形是落点 C（源码在 profile 外且不做成链接包），而那是**可以通过选择落点绕过的**，不是 DSH 的硬限制。

### 1.2 若仍要保留「独立 profile」，只允许用这三类理由

热更已被证明可行，所以「独立 profile」不再是**为了能改代码**而存在的。要保留它，必须给出**除热更以外**的理由，且只接受下面三类：

| 允许的理由 | 它解决的问题 | 现状 |
| --- | --- | --- |
| **隔离崩溃** | 实验性插件把宿主带崩，不影响正在干活的实例 | 未实测，属合理工程理由 |
| **隔离依赖版本** | 实验插件要另一套 `@deepseek-ai/*` 版本，不能污染在用 profile | 未实测，属合理工程理由 |
| **隔离权限** | 实验插件需要更大/更小的文件或网络权限 | 未实测，属合理工程理由 |

**不接受**的理由：「否则要重启」（已被 §1.1 推翻）、「否则改不了代码」（同上）。

## 2. 适配器边界声明

### 2.1 缝已经在代码里，位置是确定的

| 缝 | 位置 | 事实 |
| --- | --- | --- |
| 依赖注入 | `packages/dsh-decision/src/host/tools.ts:132-138` | `DecisionToolDeps` 四字段全注入：`agents` / `openStore` / `asker` / 可选 `projectTimeoutMs` |
| 注册口 | `tools.ts:566` | `registerDecisionTools(sink, deps)` 收**结构类型** sink，不收 `ctx.tools` ⇒ 可接任何宿主 |
| caller 层 | `src/host/caller.ts:50` | 该文件 **import 数 = 0**；`LiveAgentRegistry` 是结构接口 |
| 询问面 | `src/host/first-binding.ts:89` | `QuestionAsker` 是结构接口（`ask` / `askTimed`） |
| DSH 真实耦合 | `src/host/config.ts` | **全仓唯一** import `@deepseek-ai/*` 的文件，**2 条语句**（schemastery / cordis），4,483 B = src 的 3.6% |
| 测试独立性 | `tests/**`（9 文件 / 92 项） | 对 `@deepseek-ai` 引用数 = **0**；`host/` 44 项 **378 ms** 全绿 |

规模读数：`src/` = 9 个 `.ts` / **124,652 B**；domain+storage = 60,873 B（48.8%）、host = 63,779 B（51.2%）。

**⇒ 适配器的定义**：它只替换 `DecisionToolDeps` 的四项供给（谁来当 caller、从哪拿 store、问谁、超时多少），**其余一行不改**。

### 2.2 两条硬约束（缺一条，这个适配器就失去意义）

| # | 约束 | 不遵守会怎样 |
| --- | --- | --- |
| **a** | 必须复用 `createDecisionTools(deps)`，**不许** argv 直连 store | 六个工具契约层与 92 项测试保护不到 CLI 的真实行为 ⇒ CLI 调通了也证明不了同一件事 |
| **b** | 必须保留 `askTimed` 并给出**真实超时源** | 契约 line 80「超时什么都不写」在自然 CLI 里根本不可达 ⇒ `AskOutcome.pending` 变成死代码，测试仍全绿（`D-1164` ② 已实测这条） |

关于增量成本（`task-301` §5 [实测]）：可跑通六工具的最小 CLI = **81 行 / 3,761 B / 占 src 3.0%**，其中**领域逻辑 0 行**。

### 2.3 它不是权限边界 —— 归因退化到 OS 账户级别

这一节是本文的核心，也是所有后续文档的诚实底线。

| 层 | 是不是真约束 | 读数 |
| --- | --- | --- |
| **OS 账户** | **是**（真正的边界） | `%LOCALAPPDATA%` 下 DB 的 ACL 只有 `SYSTEM` / `Administrators` / 本用户，**无 `Authenticated Users`**；普通目录对照组是 `Authenticated Users: Modify` ⇒ 换一个 Windows 用户确实进不来 [实测] |
| **同用户内的进程** | **否** | 同用户的任意进程 `node -e` 直连 sqlite 写入成功，**DSD 的任何规则都没参与**，代价**一行** [实测] |
| **CLI vs DSH 插件** | **无差异** | 上面两行对两者同样成立 —— DSH 侧的 caller gate 保护的是「Agent 经工具调用时是不是授权 root session」，**不保护 DB 文件本身**（`D-1168` ②） |

**所以正确的表述是**：

> CLI 写入的归因**退化到 OS 账户级别** —— 能证明「这个账户做了这件事」，不能证明「这个账户里的哪个程序、受谁指使」。

**错误表述（禁止出现在任何文档）**：

- ❌「CLI 是安全的」
- ❌「CLI 有授权面」
- ❌「CLI 的 caller gate 保证了只有 Agent 能写」
- ❌「CLI 比 DSH 插件弱」（两者在这条轴上是同一个位置，`D-1168` 判据：**比较两个形态的安全性时，先问威胁模型是否同一个人**）

## 3. 最小调用面清单

### 3.1 现有六个工具（`DECISION_TOOL_NAMES`，`tools.ts:44-51`）

| 工具 | 类型 | 有无副作用 |
| --- | --- | --- |
| `decision_search` | 读 | 无 |
| `decision_get` | 读 | 无 |
| `decision_create` | 写 | 有（新增一条） |
| `decision_create_batch` | 写 | 有（批量新增） |
| `decision_update` | 写 | 有（改内容 + revision+1） |
| `decision_void` | 写 | 有（作废，不删除） |

六个工具**都不接受** `projectId` / `projectKey` 参数（契约 line 84）；项目一律来自注入的绑定。

### 3.2 从 CLI 发起**有意义**的（含必须同时满足的条件）

| 操作 | 为什么从 CLI 有意义 | 必须同时满足 |
| --- | --- | --- |
| `search` / `get`（读） | 纯读、无副作用；脚本/CI 里做「查一下这条决策还在不在」最自然 | 只需项目定位成功 |
| `create` / `create_batch`（写） | 批量导入、脚本化记录一次成型；`create_batch` 天然对应「一次导入一批」 | ① 项目**显式**给出（不猜）② 非 TTY 时必须 `--yes` ③ 记录 `entry=cli` 与自报主体 |
| `update` / `void`（写） | 修正与作废是运维动作，脚本化有意义（`void` 不删除，可恢复） | 同上三条；`update` 还需显式带 revision |

判据：「有意义」= **它不假装有权限**，只把 CLI 当一个显式动作用户意志的通道。

### 3.3 必须留在 DSH 内（CLI 做不到，不是不想做）

| 留在 DSH 的 | 为什么不能搬到 CLI | 依据 |
| --- | --- | --- |
| **caller 验证**（root agent / delegated 拒绝） | CLI 里 registry 是 CLI 自己填的字面量，**没有产生源** ⇒ 三个拒绝码「可测但非自然可达」 | `task-301` / `D-1164` ② [实测] |
| **session → project 绑定** | DSH 由宿主给 `session_id → project_id`；CLI 没有 session，只能拿 cwd 顶替 ⇒ **两者不是同一件事**，CLI 写入的归属天然弱一档 | 契约 line 78 / `task-313` §3 [实测] |
| **项目选择的问卡**（契约 line 79：`名称 · key` + 新建项目；同名靠 key 选；禁止静默自动绑定） | 问卡是 DSH 的 UI 面；CLI 只有 TTY 提示，**本会话未取得正向 TTY 样本**，无法断言等价 | 契约 line 79 / `task-313` §3.2（诚实边界） |
| **first-binding 的四步收集**（契约 line 80） | 同上；且「超时什么都不写」需要真实超时源，自然 CLI 没有（见 §2.2 b） | 契约 line 80 / `D-1164` ② |
| **跨项目视图**（`listProjects` / 跨项目检索） | 今天**没有任何工具**暴露它（见 §3.4）⇒ 不是「CLI 也能」，而是「谁都还不能」 | `tools.ts:44-51` 实测 |

### 3.4 现状缺口（**列出来是为了不顺手补**）

| 缺口 | 事实 | 处置 |
| --- | --- | --- |
| `getDecisionHistory`（修订历史） | 在 `DecisionToolStore` 接口里声明（`tools.ts:125`）、`sqlite-store.ts:870` 有实现，但**没有任何工具暴露它** | 不在本卡补。要做另开卡，且要过契约 |
| `refs`（交叉索引） | 六工具里**不存在**这个名字 | 同上；这是新面，不是「复用已有工具」 |
| `export`（导出） | 六工具里**不存在**；`package.json` 的 `exports` 只有 `./typert` 与 `./client/typert` | 同上 |
| 跨项目检索 | `searchDecisions(projectId, input)` 必须传项目；用 `listProjects` 循环实测 20 项目 / 1,000 决策 = **1 ms** | 性能不是问题，**缺的是面**。要做得显式加命令并补项目标识 |

## 4. 明确不做（四件，逐条写清怎么失败的，防后人重提）

### 4.1 不做 caller identity 伪造防护 —— 三候选全部失败

| 候选 | 思路 | 实测结局 |
| --- | --- | --- |
| **A 纯规则** | `--as <principal>` 自报，DSD 只校验它在 registry 里存在 | `root-agent` / `some-random-process` / `ROOT-AGENT` 三种声明**全部写入成功**，无一被拒。**谁能绕过：任何人；代价：换一个字符串 = 0。这是规则，不是约束** |
| **B 传输层 / 进程溯源** | 本地 pipe 拿对端 PID ⇒ 走父进程链判断调用方是不是 DSH 宿主 | **三层独立失败**，见下方展开 |
| **C broker + capability token** | 授权面留宿主侧，写操作要宿主签发的 token | 合法 CLI 与任意同用户进程**都拿到了 token**；broker 自己打印 `identifiable=false peer={}`。**谁能绕过：任何同用户进程；代价：一次 `net.connect`** |

**候选 B 的三层，每层单独就足以否决**（`D-1168` 附记已入册）：

| 层 | 实测 |
| --- | --- |
| **能力层** | Node 当 named pipe **服务端**拿到 **0 个**身份字段（`remoteAddress` / `remotePort` / `remoteFamily` 全 `undefined`，`node:net` 无 peer-cred API）。对照：PowerShell 侧 P/Invoke `GetNamedPipeClientProcessId` 能精确拿到 `clientPid=82912` ⇒ Node 要用得引 native addon 或常驻 helper（冷启动 562–1,225 ms）。替代路线「读自己 `ppid`」：`ppid` 免费，但 `ppid` → 可执行路径实测 **1,958 ms** |
| **方向层** | 实测父链 `node ← pwsh ← DeepSeek Harness.exe`。**链里出现 DSH，恰恰说明这条命令是 Agent 通过工具跑的 —— 那正是必须拒绝的情形**；真人自己在终端敲 `dsd` 时链里**没有** DSH。⇒ 按该判据实现 = 放行 Agent、拒绝人类，**方向完全颠倒**。且反向判据也只能证明「不是 Agent 跑的」，证明不了「是人在终端敲的」（定时任务 / 任何脚本链里同样没有 DSH） |
| **脱链层** | `Invoke-CimMethod Win32_Process Create` 一行 PowerShell（普通用户权限、无 UAC）把父进程重写成 `WmiPrvSE.exe`，实测 `containsDSH=False` |

**综上**：`--as` 字符串永远可伪造，而任何「进程事实」既不指向正确方向、也能一行脱链。**这不是参数写反了，死因是结构性的** ⇒ 不要因为标题只提方向层就重新尝试。

### 4.2 不做 token / broker

两个独立理由，任一成立即否决：

1. **无认证**：broker 没有任何手段分辨谁在连（实测 `identifiable=false`），签发不构成认证 ⇒ 它提供的是「同意」的假象，不是「授权」。
2. **引入长命进程**：它必须常驻一个 broker 进程，而 CLI 形态本不需要第二个长命进程 —— 把它换成另一个常驻进程，问题只是搬了个家。

附带：broker 死则写全停，**没有离线降级路径**。

### 4.3 不发明 permission model

理由只有一句：**它拿不到比「同用户进程」更多的东西。**

同用户任意进程可 `node -e` 直写 sqlite（代价一行，`task-313` §2.2 [实测]）⇒ 任何在此之上发明的权限模型都是**假的安全感**：它约束的只是「愿意走 DSD 入口的人」，而愿意走入口的人本来就不需要被约束。

唯一能给出**可量化绕过成本**的方向，是把 DB 放进另一个账户的 ACL 之下（绕过得拿到该账户凭据或管理员）。**记录在此，但明确不推荐**：代价是改 OS 账户结构，远超一个本地决策工具该付的复杂度。

### 4.4 不把 CLI 写成「安全的」

任何文档、卡面、README、报告里，CLI 的安全表述**只允许**这一种：

> 归因退化到 OS 账户级别：能证明「这个账户做了」，不能证明「这个账户里的哪个程序、受谁指使」。

理由：用户要的是**能用的工具**，不是被包装过的结论。把「有入口检查」写成「安全」，会让下一个读文档的人在错误的前提下做设计决策 —— 这正是 `D-1168` 已经付过一次的代价。

## 5. CLI 与 DSH 插件各自适用什么场景

**两者不是替代关系，是分工关系**（`D-1164`：同一注入缝上的第二个适配器）。热更已被证明可行（§1.1），所以「因为 DSH 迭代慢所以要 CLI」这个分工判据**作废**，必须用下面的差异重新分。

| 维度 | DSH 插件（主形态） | CLI（第二适配器） |
| --- | --- | --- |
| **身份 / 项目来源** | 宿主给：`session_id → project_id`，caller 是真实 root agent | cwd（需 `realpath` 归一），caller 是自报 |
| **归因质量** | 进程内知道是谁在调（可信、可归因） | 只有声明（**不可信**） |
| **适用场景** | Agent 在会话里读写决策；需要问卡（项目选择 / 新建四步）；需要 caller 语义 | 脚本 / CI / 其他工具调用；批量导入；人手动查一条 |
| **不适用** | 应当由脚本无人值守完成的批量操作 | 需要「谁在调」有意义的场合；需要问卡的交互 |
| **迭代方式** | 热更：改源码后落点 A/D 直接生效，B 档碰一次 patch 约 2.1 s | 本来就是源码级改了就改（无构建） |
| **失败模式** | 插件拖垮宿主（可用独立 profile 隔离，理由见 §1.2） | 只影响这一次命令 |

**判据（一句话分工）**：

- 需要**可信归因**或**交互式问卡** ⇒ 走 DSH 插件。
- 需要**被别的程序调用**或**无人值守批量** ⇒ 走 CLI，且结果接受「归因只到账户级」。
- 两者都不满足 ⇒ 不要为了「顺手」再造第三种入口。
